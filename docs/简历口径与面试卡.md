## 三、高频追问(10 问)

**1. 为什么用 LangGraph 不用函数串?**
状态显式声明、可持久化(checkpointer)、条件边天然适配"追问/路由/失败分支";函数串把状态藏在局部变量里,多轮和恢复都难做。

**2. MCP 和 A2A 都有了,职责怎么分?**
MCP 是**工具层**(健康数据读写、营养库、计划打卡,参数化 + 幂等 + 审计);A2A 是**Agent 服务层**(健康知识 RAG 独立进程,单独升级、单独降级)。一个是"动手",一个是"动脑"。

**3. 为什么用 pgvector 不用 Milvus?**
两个约束:数据规模(知识库 40 块,不是 40 万)和部署成本(云端 2C2G 跑不动 Milvus)。同库还能共享事务与备份,少一个中间件;检索层做了抽象,需要时可插拔换 Milvus。

**4. 双模型容灾是真实的吗?**
是。provider 链按序尝试、失败自动切换、**空正文视同失败**——之前的项目里实测过主模型把 max_tokens 全花在思考上返回空正文、自动切备用成功。当前演示环境是同一 Key 下的 pro→flash 模型级降级,第三方 provider 填配置即入链。

**5. "闭环"具体怎么调计划?**
完成率 ≥80% 且不疲劳 → 加量(单周 ≤10%);<50% 或连续疲惫 → 降档拆小目标;连续 2 次体感 ≤2 → 插恢复日;同一训练连续 4 周 → 换项建议;出差/伤病按事件重排。全部规则化,计划卡带 evidence(完成率/疲惫占比/低体感连击/事件),"为什么降强度"点开就能看到。

**6. 记忆为什么必须"确认后才写"?**
健康画像写错会污染后续所有计划和建议(比如误记"膝盖有伤"就永远不排下肢)。所以:LLM 抽取 → 校验 → 签名 token(10 分钟、防篡改)→ 用户点确认 → 落库;列表字段追加去重,单条/全部已读等状态都幂等。

**7. 安全边界怎么设计的?**
双层拦截:网关最优先(不调用路由与任何 Agent)+ RAG Agent 前置(不检索不生成)。命中高危关键词/场景 → 停止一切运动饮食建议,只给就医/急救引导(120 / 心理援助 12356)+ 免责声明;12 个用例回归(高危必拦、正常不误拦)。

**8. 评测是怎么做的?**
评测驱动迭代:意图 77 条(集合完全匹配,边界项定义"等价口径"防止拿不稳定用例凑数字);RAG 30 问答对(检索命中率/来源率 + LLM-Judge faithfulness);安全用例表驱动;端到端 39 断言。最有说服力的是检索质量三轮修复:文档级标题→小节级(43.3%→96.7%),候选窗口 8→12 + 标题/内容混合重排(→100%)。

**9. 工程上踩过最有价值的坑?**
① Windows 下 psycopg 异步不支持 Proactor 事件循环,而必须在事件循环创建前切换——`-m uvicorn` 做不到,所以写了 `run_server.py` 统一入口;② asyncpg 连接池 `pool_pre_ping` 触发 MissingGreenlet,改用 `pool_recycle`;③ SQLAlchemy `onupdate` 生成值在 commit 后被标记过期,异步上下文访问会炸——显式写时间戳。都写进验收记录了。

**10. 三个项目怎么区分?**
客服平台 = B 端一问一答 + LangGraph/RAG/MCP + 主管 HitL 审批;办公助手 = A2A + MCP 的实时事务系统(预订/报修/提醒);健康助手 = C 端**长期闭环**——记忆、主动服务、数据可视化,并且是唯一一个"成本约束驱动选型"(pgvector、透明降级)的项目。

## 四、可以现场演示的三条最短路径

1. **闭环**:记录 → 追问 → "下周排计划,周三出差" → 打卡 → 下周降档(有 evidence)
2. **记忆**:「我膝盖不好」→ 确认卡 → 重启网关 → 「那这周呢?」仍懂指代
3. **安全**:「我胸痛应该吃什么药」→ 直接拦截 + 就医引导(120)
